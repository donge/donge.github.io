mlnx_sai 到 sx_api 的映射

mlnx_sai → sx_api mapping

SAI 是厂商无关门面；厂商实现 libsai.so（mlnx_sai，开源在 Mellanox/SAI-Implementation）把 sai_* 调用翻译成 SX SDK 的 sx_api_*。对象模型一一对应：SAI 的 switch/port/vlan/route 建到 SDK 的 device/port/fdb/route 表项。

SAI is the vendor-neutral facade; the vendor implementation libsai.so (mlnx_sai, open at Mellanox/SAI-Implementation) translates sai_* calls into SX SDK sx_api_*. The object models correspond: SAI switch/port/vlan/route map to SDK device/port/fdb/route entries.

关键认知：统一 API 不代表各芯片的资源、原子性与语义相同。create-only 属性、能力查询、OID 映射、批量部分失败都需逐项核对。SAI 头（sx/sdk/sx_api_*.h）是契约。

Key insight: a unified API does not imply identical resources, atomicity or semantics across chips. create-only attributes, capability queries, OID mapping and partial bulk failures must be verified item by item. The SAI headers (sx/sdk/sx_api_*.h) are the contract.

warm-boot 与 ISSU 语义

Warm-boot & ISSU semantics

SAI warm-boot 标志区分「首次初始化」与「保留硬件转发的重启」；厂商 SAI 决定哪些状态可从硬件恢复、哪些需重建。fast/warm/ISSU 只是名称，不代表零丢包。

SAI warm-boot flags distinguish first init from restart-with-retained-forwarding; the vendor SAI decides which state recovers from hardware versus is rebuilt. fast/warm/ISSU are labels, not proof of zero loss.

验证要覆盖重启期间的新流、旧流、路由变化与异常报文；对账「期望态 / 软件已应用态 / 硬件实际态」，避免简单重放造成资源泄漏或覆盖更新后的配置。

Validation must cover new and existing flows, route changes and exceptional packets during restart; reconcile desired / software-applied / actual-hardware state to avoid resource leaks or overwriting newer configuration on blind replay.

SONiC 到 SDK 的调用路径

SONiC → SDK call path

完整路径：CONFIG_DB/APPL_DB → orchagent → SAI 对象 → ASIC_DB/syncd → libsai → sx_api → /dev/sxcdev → sx_core.ko → ASIC。各数据库反映不同阶段，不是彼此的镜像。

Full path: CONFIG_DB/APPL_DB → orchagent → SAI objects → ASIC_DB/syncd → libsai → sx_api → /dev/sxcdev → sx_core.ko → ASIC. Each DB reflects a different stage and is not a mirror of the others.

SDK 调试与可观测

SDK debug & observability

SDK 自带调试工具（syncd 容器内 /usr/bin），配合内核态面：/proc/mlx_sx/*、/sys/module/sx_core/asic*、SPICE 的 debugfs /nvswitch，以及 sx_emad_dump.ko 的 netlink EMAD 旁路抓取。

The SDK ships debug utilities (in the syncd container /usr/bin), paired with kernel-side surfaces: /proc/mlx_sx/*, /sys/module/sx_core/asic*, the SPICE debugfs /nvswitch, and the sx_emad_dump.ko netlink EMAD tap.

分层定位：应用/collective → GPU/NIC → 链路 → 队列/转发 → 控制面 → SDK/ASIC。先保留现场（寄存器、计数器、版本快照）再改配置，避免恢复动作抹掉根因证据。

Localize in layers: app/collective → GPU/NIC → link → queues/forwarding → control plane → SDK/ASIC. Preserve evidence (registers, counters, version snapshots) before changing config so recovery does not erase the root cause.

企业版与社区版

Enterprise vs community

NVIDIA 同时提供社区 SONiC 与企业 SONiC；二者的 SAI 扩展、SDK 版本绑定与平台服务不同。同一接口名在不同版本可能有不同语义。

NVIDIA offers both community and enterprise SONiC; their SAI extensions, SDK version binding and platform services differ. The same interface name may carry different semantics across versions.

跨版本升级需核对 SAI 头/扩展、SDK 版本兼容矩阵与 warm-boot 支持；schema 迁移不可逆时，回滚需要兼容数据，而不仅是旧镜像可启动。

Cross-version upgrades must check SAI headers/extensions, the SDK compatibility matrix and warm-boot support; when schema migration is irreversible, rollback needs compatible data, not merely a bootable old image.
