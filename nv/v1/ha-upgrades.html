原理与实现路径

Mechanisms & implementation path

Precheck → freeze → checkpoint → restart → restore → reconcile
         → health gate → resume; failures follow explicit recovery policy

故障模型

Failure model

分别处理进程、OS、SDK、固件、ASIC、链路、电源和管理网失效；明确故障域、保留状态、恢复目标与检测时间。

Treat process, OS, SDK, firmware, ASIC, link, power and management-network failures separately. Define failure domains, retained state, recovery targets and detection time.

为每种故障写清检测信号、检测时限、可保留状态和允许影响。链路失败可能由协议处理，SDK 卡死可能需要服务隔离；不应对所有故障统一使用整机重启，避免扩大故障域。

Define detection signals/deadlines, retained state and allowed impact for each failure. Protocols may handle link failure; SDK hangs may need service isolation. Avoid rebooting the entire system for every fault and expanding the failure domain.

Warm restart

Warm restart

冻结/排空变更 → 保存必要状态 → 保留可保持的硬件转发 → 恢复映射 → reconcile → 恢复协议/学习；设置超时与 cold fallback。

Freeze/drain changes → save required state → retain supported hardware forwarding → restore mappings → reconcile → resume protocols/learning. Set timeouts and cold-recovery fallback.

转发保留只是 warm restart 的一部分：控制协议超时、邻居老化、MAC 学习与链路事件仍在发生。验证重启期间新流、旧流、路由变化和异常报文的行为，而非只测一条静态长流。

Retained forwarding is only part of warm restart: protocol timers, neighbor aging, MAC learning and link events continue. Test new and existing flows, route changes and exceptional packets during restart, not only one static long-lived flow.

一致性风险

Consistency risks

软件成功但硬件未写入、重复创建、恢复依赖倒序、旧通知覆盖新态、OID/计数器变化；warm/fast/ISSU 名称不能证明零丢包。

Software success without hardware application, duplicate creation, reversed restore dependencies, stale notifications and OID/counter changes. Warm/fast/ISSU labels do not prove zero loss.

测试结果未知的边界：应用在提交后崩溃、设备在确认前 reset、消息在持久化前丢失。恢复流程应能识别“未做、已做、部分做”，否则简单重放可能泄漏资源或覆盖更新后的配置。

Test unknown outcomes: an application crashes after submission, a device resets before acknowledgement, or a message is lost before persistence. Recovery must distinguish not applied, applied and partially applied; blind replay can leak resources or overwrite newer configuration.

升级韧性

Upgrade resilience

Schema 迁移、双镜像/签名、版本互通、健康门槛、回滚及数据兼容；限流、隔离、watchdog、退避与容量余量防止级联故障。

Schema migration, dual images/signatures, interoperability, health gates, rollback and data compatibility. Rate limits, isolation, watchdogs, backoff and spare capacity limit cascading failures.

回滚需要兼容数据而不仅是旧镜像可启动。新版本 schema 若不可逆，旧软件可能无法读取配置；升级前保存可恢复快照，并在健康检查失败时明确自动回滚条件、超时与人工介入点。

Rollback needs data compatibility, not merely a bootable old image. Irreversible schema changes may prevent old software reading configuration. Save recoverable snapshots and define rollback triggers, deadlines and intervention points for failed health checks.

状态保留清单

State-retention inventory

对 MAC、route、neighbor、ACL、QoS、端口、计数器和协议会话逐项记录：存在哪里、谁重建、允许陈旧多久、恢复前能否接流量。数据面保留与控制面 GR 是不同机制；邻居或链路变化可能让保留转发迅速失效，需明确动态事件处理。

For MACs, routes, neighbors, ACLs, QoS, ports, counters and sessions, record location, reconstruction owner, allowed staleness and readiness gating. Data-plane retention differs from protocol GR; neighbor/link changes can invalidate retained forwarding, requiring explicit event handling.

升级时序与回滚

Upgrade timeline & rollback

预检查版本/空间/资源→冻结配置写入→记录 checkpoint→重启目标组件→恢复映射→对账→健康验证→解冻。每阶段有超时和退出策略；rollback 需要旧代码能读数据或可恢复旧快照。若新版本已经改变不可逆硬件/配置状态，应在设计阶段明确不可自动回滚的边界。

Precheck versions/space/resources→freeze writes→checkpoint→restart target→restore mappings→reconcile→health-check→unfreeze. Each phase needs deadlines/exits. Rollback needs old-readable data or restorable snapshots. Define boundaries for irreversible hardware/configuration changes before deployment.

验收：不仅是零丢包

Acceptance: more than zero loss

同时测试静态长流、新流建立、MAC 移动、路由 churn 和链路故障。记录丢包、乱序、控制会话重建、配置可用时间和资源残留。即使一条长流不断，若新路由永远无法下发也不能判升级成功；应验证完整服务能力恢复。

Test long-lived flows, new flows, MAC moves, route churn and link failures together. Record loss/reordering, session reconstruction, configuration availability and residual resources. An uninterrupted long flow does not prove success if new routes cannot be installed; validate full service restoration.
