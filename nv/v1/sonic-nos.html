系统组成

Components

管理/配置、协议进程、状态库、编排、平台服务、遥测、升级；进程隔离不等于状态隔离，必须明确所有权与恢复顺序。

Management/configuration, protocol daemons, state stores, orchestration, platform services, telemetry and upgrades. Process isolation does not imply state isolation; define ownership and recovery ordering.

一个服务 ready 不代表整个交换栈 ready。分别定义配置接受、协议邻接、硬件初始化和转发就绪；服务依赖启动顺序也应有超时与降级，否则单个模块卡住可能阻塞整个系统。

A ready service does not imply a ready switch. Define configuration acceptance, protocol adjacency, hardware initialization and forwarding readiness separately. Add deadlines and degradation to startup dependencies so one hung module cannot block everything.

SONiC 路径 [S3]

SONiC path [S3]

APPL_DB → orchagent → SAI 对象 → ASIC_DB/syncd → SAI 实现；CONFIG_DB、STATE_DB、COUNTERS_DB 用途不同，具体路径按版本源码核对。

APPL_DB → orchagent → SAI objects → ASIC_DB/syncd → SAI implementation. CONFIG_DB, STATE_DB and COUNTERS_DB serve different roles; verify paths against the version's source.

排查配置未生效时追踪同一对象：配置库是否接受，应用状态是否生成，orchagent 是否满足依赖，syncd/SAI 是否返回错误，硬件表是否存在。各数据库反映不同阶段，不应直接当作彼此的镜像。

Trace one object end to end: configuration accepted, application state generated, dependencies satisfied by orchagent, syncd/SAI result, and actual hardware entry. Databases represent different stages rather than interchangeable mirrors.

协议与服务

Protocols & services

FRR 等路由栈到内核/编排同步；端口/VLAN/邻居/路由依赖；容器生命周期、watchdog、平台抽象、schema 迁移、就绪检查与配额。

Synchronization from routing stacks such as FRR to the kernel/orchestrator; port/VLAN/neighbor/route dependencies. Container lifecycle, watchdogs, platform abstraction, schema migration, readiness and quotas.

路由 daemon 更新可能比 ASIC 编程快几个数量级。需要合并同一前缀的过时更新、保留最后目标态并控制队列长度；同时确认删除和创建的依赖不会因合并而被错误跳过。

Routing daemons may produce updates far faster than ASIC programming. Coalesce obsolete updates for the same prefix, retain the latest desired state and bound queues. Ensure coalescing does not incorrectly skip create/delete dependencies.

异常恢复

Recovery

DB 断连、事件丢失、进程重启、SDK 卡死、对象孤儿、软硬漂移；提供 reconcile 和诊断快照。数据库记录不等于硬件已成功应用。

DB disconnects, lost events, daemon restarts, hung SDKs, orphan objects and state drift. Provide reconciliation and diagnostic snapshots. A database entry does not prove hardware application.

恢复时先确定“谁是事实来源”：持久配置、控制协议还是硬件保留状态。硬件已有对象不能简单全部重建；通过稳定业务键对齐临时 OID，并在对账完成前限制依赖该状态的新操作。

Choose the source of truth during recovery: persisted configuration, protocols or retained hardware state. Do not blindly recreate existing hardware objects. Match temporary OIDs through stable semantic keys and gate dependent operations until reconciliation completes.

路由下发链路走读

Walking the route-programming path

为前缀记录配置/协议来源、应用库键、orchagent 依赖、SAI 对象关系、syncd 结果及硬件条目。每阶段可能接受但尚未完成；排障时报告“卡在哪一阶段、等待谁、队列多久”，比“数据库里有”更可执行。具体数据库与进程路径以目标 SONiC 分支为准。

Track a prefix's config/protocol source, application key, orchagent dependencies, SAI object graph, syncd result and hardware entry. Acceptance may precede completion at each stage. Report the blocked stage, dependency and queue age, not merely database presence. Follow the target SONiC branch's exact paths.

案例：邻居晚到

Case: late neighbor resolution

路由先到而邻居未解析时，编排层应挂起依赖并可观测，不能忙循环重试。邻居就绪后重新调度；若路由此时已撤销，必须检查最新目标态再提交。把 pending 原因、数量和最长等待时间做成指标，可区分正常异步依赖与永久卡死。

When a route precedes neighbor resolution, orchestration should expose pending dependencies rather than busy-retry. Reschedule on readiness, but recheck current intent because the route may already be withdrawn. Metrics for pending reason/count/oldest age separate normal asynchrony from permanent stalls.

故障恢复流程

Recovery flow

停止某个进程后保留其他组件运行，重启时先连接状态库、重建依赖、核对硬件，再恢复新更新。检查 DB 重连是否重放遗漏事件，旧 ASIC OID 是否仍可用，配置 schema 是否匹配。不能把容器 restart 成功等同于转发状态恢复成功。

Restart one process while others remain active: reconnect stores, reconstruct dependencies, reconcile hardware, then accept new updates. Check missed events after DB reconnect, retained ASIC OIDs and schema compatibility. Container restart success is not forwarding-state recovery.
