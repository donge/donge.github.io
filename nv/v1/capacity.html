负载输入

Workload inputs

端点/GPU 数、并发作业、流数、消息尺寸、突发持续时间、东西向流量、租户隔离、拓扑亲和性。

Endpoints/GPUs, concurrent jobs, flow count, message sizes, burst duration, east–west traffic, tenant isolation and topology affinity.

平均带宽相同的两种负载可能需要不同缓冲：均匀流量较平滑，同步发送会瞬间形成 incast。需求输入应包含到达速率随时间的变化、消息分布、突发同步程度和慢接收端比例，再生成可重复的流量模型。

Equal average bandwidth can require very different buffering: steady traffic is smooth, synchronized senders create incast. Capture time-varying arrival rates, message distributions, burst synchronization and slow-receiver fraction before building a repeatable traffic model.

资源维度

Resource dimensions

端口/速率、Tb/s 与 pps、MAC/路由/邻居/ECMP/ACL/隧道数量、队列/缓冲、CPU/内存、表项编程速率与遥测开销。

Ports/speeds, Tb/s and pps, MAC/route/neighbor/ECMP/ACL/tunnel scale, queues/buffers, CPU/memory, programming rate and telemetry overhead.

建立资源表：容量、当前使用、峰值、预留、分配粒度和释放延迟。路由规模之外还要估算下一跳组、邻居和计数器；大量短生命周期对象可能在删除尚未完成时再次申请，形成瞬时容量峰值。

Track capacity, current/peak usage, reserve, allocation granularity and release delay. Budget next-hop groups, neighbors and counters as well as routes. Short-lived objects can create transient peaks when new allocations precede completed deletions.

共享限制

Shared limits

SRAM/TCAM、IPv6 宽表项、ACL key/action、计数器可能争用资源；各特性独立最大值不能相加。分析最坏组合、余量和降级顺序。

SRAM/TCAM, wide IPv6 entries, ACL keys/actions and counters may compete for resources. Independent feature maxima are not additive. Budget worst-case combinations, headroom and degradation order.

先测试混合业务配置，而非分别测每张表的最大值。例如宽 IPv6 ACL 可能消耗更多切片，使其他 ACL 的可用容量下降。预留策略应覆盖故障重路由、升级双份状态和表项重建，而不只是正常稳态。

Test mixed configurations, not just individual table maxima. Wide IPv6 ACLs may consume additional slices and reduce other ACL capacity. Reserve space for rerouting, duplicated upgrade state and reconstruction, not only steady operation.

验收指标

Acceptance metrics

明确帧长/封装/单双向口径；测 p50/p99/p99.9 延迟、丢包、收敛、恢复及训练 step time；固定规模、故障条件、容差与基线。

Specify frame size, encapsulation and directional accounting. Measure p50/p99/p99.9 latency, loss, convergence, recovery and training step time with fixed scale, failure conditions, tolerances and baselines.

明确起止时间和计数位置：链路断开到首次恢复报文，与断开到持续稳定转发不是同一指标。尾延迟需要足够样本；记录预热、运行时长、重复次数和异常值处理，避免平均值掩盖短时中断。

Define measurement boundaries: time to the first restored packet differs from time to sustained forwarding. Tail latency requires sufficient samples. Record warm-up, duration, repetitions and outlier handling so averages do not hide brief outages.

容量不是单一最大值

Capacity is not one maximum

对资源 r 建立 Σ(n_i×c_ir)+reserve_r≤capacity_r。n_i 是功能对象数量，c_ir 是它对该资源的实际消耗；系数可能随 key 宽度和配置变化。至少建模条目、动作、计数器、下一跳组成员与缓冲。实测获得系数后，还要验证分配碎片和不同插入顺序，因为数学上能放下不代表硬件分配器一定成功。

For each resource r require Σ(n_i×c_ir)+reserve_r≤capacity_r. Counts n_i and costs c_ir may vary with key width/configuration. Model entries, actions, counters, group members and buffers. Derive costs empirically and test fragmentation/insertion order: aggregate capacity does not guarantee allocator success.

算例：更新速率与积压

Example: update rate & backlog

假设输入持续 30k 次/s，硬件确认仅 20k 次/s，未合并队列每秒增加 10k；每项含元数据占 256B，约增长 2.56MB/s，60 秒即约 154MB。加大队列只推迟故障。可按同一对象合并到最后目标态、限制入口速率或增加设备编程能力；合并不能跨越必须保留的依赖与屏障。

With 30k updates/s arriving and 20k/s confirmed, an uncoalesced queue grows by 10k/s. At 256B per item including metadata, that is about 2.56MB/s or 154MB in 60s. Larger queues only defer failure. Coalesce by object, limit admission or increase programming capacity, while preserving dependencies and required barriers.

验收矩阵

Acceptance matrix

分别测稳态满容量、突发更新、故障恢复双份对象和长期 churn。记录拒绝配置是否明确、已存在业务是否继续工作、资源释放延迟、p99 编程时间和峰值内存。容量目标应同时给 workload、配置组合、版本和失败比例；脱离这些条件的“支持百万路由”不足以完成设计评估。

Test full steady state, update bursts, duplicated recovery objects and sustained churn. Record explicit rejection, continued existing service, resource-release delay, p99 programming time and peak memory. State workload, feature mix, version and failure ratio alongside capacity; a standalone million-route claim is insufficient.
