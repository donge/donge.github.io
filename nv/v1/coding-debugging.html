编程基础

Programming

C/C++ 指针、位运算、结构布局、所有权、RAII、UB/ABI；Python 测试和自动化；Shell 系统诊断。状态机与错误路径应可测试。

C/C++ pointers, bit operations, layouts, ownership, RAII and UB/ABI; Python for testing/automation; shell for diagnostics. Make state machines and failure paths testable.

C/C++ 边界代码优先明确所有权与长度：谁申请、谁释放、是否跨线程、是否异步持有。对报文和固件输入避免未对齐访问、整数溢出和信任长度字段；错误路径必须与正常路径同样完整。

In C/C++ boundary code, specify ownership and lengths: allocator, releaser, cross-thread access and asynchronous retention. Avoid unaligned access, integer overflow and trusting packet/firmware length fields. Make failure cleanup as complete as normal processing.

构建与交付

Builds & delivery

交叉编译、toolchain/sysroot、Make/CMake、静态/动态链接、符号、依赖锁定、可复现构建、镜像裁剪与版本矩阵。

Cross-compilation, toolchains/sysroots, Make/CMake, static/dynamic linking, symbols, pinned dependencies, reproducible builds, image trimming and version matrices.

记录 compiler、链接器、头文件、SDK 和固件版本；同名库不同 ABI 可能在链接时通过却运行出错。保留符号与构件哈希，使现场 core 能精确对应源码与可执行文件。

Record compiler, linker, headers, SDK and firmware versions. ABI-incompatible libraries may link but fail at runtime. Retain symbols and artifact hashes so field cores map exactly to source and binaries.

诊断工具

Diagnostic tools

gdb/core、perf、ftrace/trace-cmd、strace、bpftrace；KASAN/KCSAN/lockdep、ASan/UBSan；评估工具对负载和时序的扰动。

gdb/cores, perf, ftrace/trace-cmd, strace and bpftrace; KASAN/KCSAN/lockdep and ASan/UBSan. Account for instrumentation effects on load and timing.

先选工具回答一个问题：perf 找 CPU 热点，trace 找时间顺序，core 找崩溃现场，sanitizer 找内存/竞争错误。调试版本会改变时序，因此需把最小复现与接近生产的负载验证结合起来。

Pick tools for specific questions: perf for CPU hotspots, tracing for ordering, cores for crash state and sanitizers for memory/race faults. Debug builds alter timing, so combine minimal reproducers with production-like load validation.

质量检查

Quality checks

正常/异常/并发/重启路径；输入与溢出、锁范围、清理、兼容；静态检查、单元/集成/硬件回归、可追溯构件和故障复现。

Normal, failure, concurrency and restart paths; input/overflow checks, lock scope, cleanup and compatibility. Use static analysis, unit/integration/hardware regression, traceable builds and reproducers.

回归应验证外部不变量而不是复制实现：失败后无孤儿资源、重复请求不改变结果、重启后状态收敛、满表时已有转发仍满足策略。把复现步骤、输入、种子和环境快照留给 CI。

Test external invariants rather than duplicate implementation: no orphan resources after failure, idempotent requests, convergence after restart and defined behavior for existing traffic at capacity. Preserve reproducers, inputs, seeds and environment snapshots in CI.

边界代码审查样例

Boundary-code review example

解析固件长度字段时先验证最小头长，再检查声明长度≤实际缓冲长度，最后计算偏移；加法/乘法需防溢出，不能先溢出后比较。跨 ABI 的结构不应假定编译器 padding 一致；使用明确字段布局和字节序转换，并验证未知字段/版本的处理。

Validate minimum headers, then declared length≤buffer length, then offsets; guard arithmetic before overflow. Cross-ABI structures must not assume compiler padding. Specify layouts/endianness and test unknown fields/versions.

可复現错误报告

Reproducible defect report

最小报告包括构件哈希、符号、配置、拓扑、触发序列、随机种子、预期不变量和实际证据。性能问题还需 CPU 型号、频率策略、NUMA、包长和 offered load。仅提供栈顶函数或“偶发卡死”无法区分内存损坏、锁等待和设备不完成。

A minimal report includes artifact hash, symbols, configuration, topology, trigger sequence, random seed, expected invariant and evidence. Performance reports also need CPU, frequency policy, NUMA, packet size and offered load. A top stack frame or occasional hang cannot distinguish corruption, lock waits and missing device completion.

回归策略

Regression strategy

为修复写能触发旧错误且验证外部行为的测试；不要断言内部函数调用顺序，除非那本身是接口合约。高风险路径增加失败注入与 repeated create/delete；发布构件保留符号映射，使现场 core 可精确关联，避免用相近版本猜测地址。

Write a regression that triggers the old defect and verifies observable behavior. Avoid internal call-order assertions unless contractual. Add fault injection and repeated create/delete for risky paths. Retain symbol mappings for exact field-core decoding instead of guessing from nearby versions.
