并行方式

Parallelism

数据、张量、流水线、专家并行的消息尺寸、通信量、同步频率和拓扑敏感度不同；单一链路带宽不能代表训练效率。

Data, tensor, pipeline and expert parallelism differ in message sizes, communication volume, synchronization and topology sensitivity. Link bandwidth alone does not represent training efficiency.

数据并行常同步梯度，张量并行可能频繁交换中间结果，流水线并行受阶段间传输影响，专家并行存在分派/聚合不均衡。把这些模式映射到消息频率、同步点和网络热点，再决定拓扑与 QoS。

Data parallelism often synchronizes gradients; tensor parallelism frequently exchanges intermediate results; pipeline parallelism depends on stage transfers; expert parallelism can create dispatch/combine imbalance. Map message frequency, synchronization and hotspots before choosing topology and QoS.

Collectives [S7]

Collectives [S7]

AllReduce 规约后分发；AllGather 收集后分发；ReduceScatter 规约后分片；另有 Broadcast/Reduce、点对点和 All-to-All 通信模式。

AllReduce reduces and distributes; AllGather gathers and distributes; ReduceScatter reduces and partitions. Also consider Broadcast/Reduce, point-to-point and all-to-all communication patterns.

Collective 的正确性依赖参与 rank 和调用参数相匹配，错误可能表现为 hang 而非网络报错。性能分析时区分算法带宽与经归一化的总线带宽；不同消息尺寸会使启动延迟或传输带宽成为主导。

Collective correctness depends on matching participating ranks and call parameters; mistakes may appear as hangs rather than network errors. Distinguish algorithm bandwidth from normalized bus bandwidth. Startup latency or transfer bandwidth dominates at different message sizes.

瓶颈链

Bottleneck chain

GPU ↔ PCIe/NVLink ↔ NIC ↔ fabric；NUMA、GPU/NIC affinity、GPUDirect RDMA、incast、热点、微突发；barrier 放大慢 rank 的尾延迟。

GPU ↔ PCIe/NVLink ↔ NIC ↔ fabric. NUMA, GPU/NIC affinity, GPUDirect RDMA, incast, hotspots and microbursts; barriers amplify slow-rank tail latency.

若某个 rank 因 PCIe/NUMA 较慢，其他 rank 可能在同步点等待，从而出现网络利用率低但作业很慢。先对比每 rank 完成时间和 NIC 流量，再测单机、两机和全规模，定位瓶颈出现的层级。

A rank slowed by PCIe/NUMA can leave others waiting at barriers, producing low network utilization but poor job performance. Compare per-rank completion and NIC traffic, then test single-node, two-node and full-scale cases to locate the bottleneck.

验证变量

Validation variables

测 step time、GPU 等待、作业完成时间、有效带宽/p99；覆盖大小消息、多作业、多 rail、rank placement、Ring/Tree/分层算法和故障。

Measure step time, GPU waiting, job completion, effective bandwidth and p99. Cover message sizes, multiple jobs/rails, rank placement, ring/tree/hierarchical algorithms and failures.

实验应固定通信算法、消息大小、rank 映射与背景负载，逐项改变一个因素。除平均吞吐外记录最慢 rank、尾部 step time 和故障后恢复；更高链路吞吐若未改善作业时间，可能不是有效优化。

Fix algorithm, message size, rank mapping and background load, then vary one factor. Record the slowest rank, tail step time and post-failure recovery as well as throughput. Higher link throughput may be irrelevant if job time does not improve.

从应用到网络矩阵

From applications to traffic matrices

为每个 rank 对收集 bytes、message count、size distribution 与通信阶段，形成随时间变化的流量矩阵。相同总 bytes 的 All-to-All 与 Ring 对链路竞争完全不同；rank placement 决定哪些通信跨机架。再将矩阵投影到 fabric 路径，找出热点与同步突发。

Build time-varying rank-pair matrices of bytes, message counts, sizes and phases. Equal total bytes in all-to-all and ring produce different contention; placement determines cross-rack traffic. Project the matrix onto fabric paths to locate hotspots and synchronized bursts.

实例：慢 rank 放大

Example: slow-rank amplification

若 63 个 rank 每阶段 8ms 完成、1 个需 12ms，同步阶段可能被 12ms 者限制，而其他 GPU 在等待。总网络利用率不高不能排除问题。比较 rank/NIC/NUMA 映射，交换慢 rank 的放置再重测；若慢点跟随物理位置，优先查主机和路径，若跟随任务，查负载不均。

If 63 ranks finish a phase in 8ms and one takes 12ms, synchronization may be limited by the 12ms rank while others wait. Low utilization proves little. Swap placement: if slowness follows hardware, inspect hosts/paths; if it follows work, inspect imbalance.

指标与对照

Metrics & controls

同时报告 algorithm bandwidth、消息大小、rank 数、collective 时长分布、GPU 空闲和作业 step time。固定算法选择与 warm-up，比较单机、两机、跨机架和全集群。性能改善必须能在同一工作负载下重复，而不是通过缩小消息、减少参与者或改变并行策略获得不可比结果。

Report algorithm bandwidth, message size, ranks, collective-time distribution, GPU idle and step time. Fix algorithm/warm-up and compare single-node, two-node, cross-rack and full scale. Repeat improvements on the same workload rather than changing sizes, ranks or parallelism into incomparable results.
