信任边界

Trust boundaries

管理 API、SSH/SNMP、协议邻居、控制报文、租户与供应链；使用最小权限、RBAC/AAA、审计、管理 VRF/OOB 和服务隔离。

Management APIs, SSH/SNMP, protocol peers, control packets, tenants and supply chains. Apply least privilege, RBAC/AAA, auditing, management VRF/OOB and service isolation.

按攻击者能接触的位置建模：租户端口、管理网络、内部服务和更新服务器各自权限不同。限制控制报文上送速率，同时保留必要诊断与协议处理能力，避免防护策略本身导致设备失联。

Model access from tenant ports, management networks, internal services and update servers separately. Limit control-packet punts while preserving required diagnostics and protocol handling so protection itself does not make the device unreachable.

平台保护

Platform protection

Secure boot、签名升级、密钥管理、mTLS、敏感日志脱敏；保护固件回滚路径，检查构件来源和完整性。

Secure boot, signed updates, key management, mTLS and sensitive-log redaction. Protect firmware rollback paths and verify artifact provenance and integrity.

启动信任链需要从可信根验证下一阶段，更新包需验证签名和适配型号。密钥轮换与恢复流程同样重要：不能只设计“拒绝坏镜像”，还要确保有效恢复镜像和凭据可用。

A boot chain verifies each next stage from a trusted root; updates need signature and model checks. Key rotation and recovery matter too: rejecting bad images is insufficient without usable trusted recovery images and credentials.

网络与 API

Network & API protection

CoPP/CPU policer、ACL、storm control、max-prefix、uRPF、邻居表保护；API 鉴权/schema/配额/限速/幂等，失败不留隐蔽部分状态。

CoPP/CPU policers, ACLs, storm control, max-prefix, uRPF and neighbor protection. API authorization/schema/quotas/rate limits/idempotency; failures must not leave hidden partial state.

CoPP 保护 CPU，并不代替数据面 ACL；ACL 也不一定能阻止所有协议状态耗尽。验证正常控制流与攻击流混合时的行为，监测 policer drop 和邻接稳定性，防止合法路由更新被饿死。

CoPP protects the CPU but does not replace data-plane ACLs; ACLs may not prevent every protocol-state exhaustion attack. Mix legitimate and attack traffic in tests, monitoring policer drops and adjacency stability to avoid starving valid route updates.

长期维护

Long-term maintenance

SBOM/CVE、许可证、依赖固定、LTS/backport、支持版本窗口、可复现构建；安全补丁需回归功能、性能、升级与回滚。

SBOM/CVE tracking, licenses, pinned dependencies, LTS/backports, supported-version windows and reproducible builds. Regress functionality, performance, upgrades and rollback after security patches.

漏洞修复应考虑实际启用组件与可达攻击面，但不能只看组件是否对外监听。依赖升级后还要检查 ABI、镜像大小、启动时间和性能；记录可重建的依赖版本及补丁来源。

Assess enabled components and reachable attack surfaces, not just externally listening services. After dependency updates, check ABI, image size, boot time and performance. Record reproducible dependency versions and patch provenance.

控制面资源耗尽模型

Control-plane exhaustion model

攻击报文可通过 trap 消耗 CPU、队列、邻居或日志空间。为每个入口定义分类和上送策略、速率/突发配额、状态表上限和丢弃计数。仅限制 pps 仍可能遗漏高成本报文；按处理成本与合法协议需求做分级预算，并验证正常邻接不会被防护误伤。

Trapped packets can exhaust CPU, queues, neighbors or logs. Define classification/punt policies, rate/burst budgets, state limits and drop counters per ingress. Pps limits alone may miss expensive packets; budget by processing cost and legitimate protocol needs and verify valid adjacencies survive.

安全更新的工程路径

Engineering secure updates

校验签名和型号→验证版本依赖→确认恢复介质→试运行→健康门槛→切换。签名有效不代表固件与 SDK 兼容；回滚保护也可能阻止紧急恢复，所以需设计受控恢复路径。密钥不可写进日志或普通配置导出，构件与来源用非敏感哈希追踪。

Verify signature/model→dependencies→recovery medium→trial→health gate→switch. Valid signatures do not prove SDK compatibility; rollback protection can impede recovery, so design controlled recovery paths. Keep keys out of logs/config exports and track artifacts through non-sensitive hashes.

验证案例

Validation case

将合法 BGP/ARP/ND 与高频异常报文混合，检查 CoPP drop、CPU 和邻接稳定性；模拟日志磁盘满、管理 API 超配额、无效签名和不匹配镜像。成功标准包括防护生效、错误可诊断、管理恢复可用和数据面影响有界。

Mix valid BGP/ARP/ND with high-rate malformed traffic and inspect CoPP drops, CPU and adjacency stability. Test full log disks, API quotas, invalid signatures and incompatible images. Require effective protection, actionable errors, management recovery and bounded data-plane impact.
