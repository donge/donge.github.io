验证层级

Test layers

单元 → API contract → 模拟 ASIC → 仿真/FPGA → 真硬件 → 多交换机 → AI 负载；虚拟测试不证明真实资源与时序。

Unit → API contract → simulated ASIC → emulation/FPGA → hardware → multiswitch → AI workloads. Virtual testing does not prove real resource or timing behavior.

Mock 擅长验证 API 调用与错误处理，无法证明实际队列、DMA 和芯片资源行为。把同一不变量跨层复用，例如“删除后无引用残留”，并在真硬件上增加时序、并发和满资源条件。

Mocks validate API interactions and errors but cannot prove real queue, DMA or chip-resource behavior. Reuse invariants such as no dangling references after deletion across layers, adding timing, concurrency and exhaustion on hardware.

功能与压力

Functional & stress

L2/L3/ACL/QoS/隧道、非法输入、满表、依赖和组合；最小帧/IMIX/Jumbo、全端口、route churn、MAC move、微突发和长期 soak。

L2/L3/ACL/QoS/tunnels, invalid inputs, full tables, dependencies and combinations; minimum frames/IMIX/jumbo, all ports, route churn, MAC moves, microbursts and long soaks.

组合测试应覆盖共享资源冲突：满路由+宽 ACL+隧道+计数器，或多播+镜像+拥塞。用边界值与成对组合缩小空间，再对高风险组合做专项压力，避免只测试各功能单独开启。

Cover shared-resource interactions: full routing tables plus wide ACLs, tunnels and counters, or multicast plus mirroring and congestion. Use boundaries/pairwise coverage, then stress high-risk combinations rather than only isolated features.

故障与恢复

Faults & recovery

Link flap、进程 kill、SDK timeout、DB 断连、丢失/重复事件、firmware reset、OOM、电源/散热故障；检查恢复上界、回滚与软硬一致性。

Link flaps, process kills, SDK timeouts, DB disconnects, lost/duplicate events, firmware resets, OOM and power/thermal failures. Check recovery bounds, rollback and state consistency.

故障测试先定义可接受中断和最终状态，再在提交前、提交中、提交后分别注入故障。自动采集资源快照和恢复时间，确保“服务恢复”不是靠泄漏旧对象或跳过配置实现的。

Define acceptable interruption and final state before injecting faults before, during and after submission. Collect resource snapshots and recovery timing automatically so apparent recovery is not achieved by leaking old objects or skipping configuration.

工具与口径

Tools & methodology

Scapy/PTF、TRex、硬件流量仪、iperf3、RDMA perftest、nccl-tests；固定版本/拓扑/负载，报告置信区间；软件发生器受 CPU/NIC 限制。

Scapy/PTF, TRex, hardware traffic generators, iperf3, RDMA perftest and nccl-tests. Fix versions/topology/load and report confidence intervals; software generators are CPU/NIC-limited.

流量发生器必须证明自身有余量：测 CPU、NIC 队列、发送丢包与接收能力。测试报告同时给 offered load 与 achieved throughput；只报告应用发送速率可能把发生器瓶颈误当交换机限制。

Verify generator headroom with CPU, NIC queues, TX drops and RX capacity. Report offered load and achieved throughput together. Application send rate alone can misattribute generator limits to the switch.

基于不变量的测试

Invariant-based testing

建立“每个路由引用有效下一跳、总资源有界、重复请求幂等、重启最终收敛、失败不破坏无关业务”等不变量。用随机操作序列生成 create/set/delete/reset，同时保留 seed 和事件日志。Oracle 同时观察期望模型、控制态和真实报文，避免测试只验证 mock 是否按预期被调用。

Define invariants: valid next-hop references, bounded resources, idempotency, restart convergence and unrelated-service preservation. Generate create/set/delete/reset sequences with saved seeds/logs. Compare a reference model, control state and real packets rather than merely checking mock calls.

矩阵压缩与高风险组合

Reducing the matrix

全组合空间常不可穷尽：先按共享资源、依赖和历史缺陷识别高风险交互，再用 pairwise 覆盖普通组合。对 full-table+warm restart、tunnel+ACL+mirror、PFC+链路降速等保留专项。单特性通过不能自动覆盖共享 stage、buffer 和计数器冲突。

Exhaustive combinations are often infeasible. Identify high-risk interactions from shared resources, dependencies and past defects, then use pairwise coverage elsewhere. Keep dedicated full-table+restart, tunnel+ACL+mirror and PFC+degraded-link tests; isolated feature passes do not cover shared-stage/buffer/counter conflicts.

结果可解释性

Interpretable results

每次运行记录 offered load、接收率、丢包位置、发生器 CPU/NIC、版本、拓扑与温度。失败先分类为产品缺陷、环境限制、发生器不足或测试不确定；不能直接重跑直到绿。长期 soak 还需拟合资源趋势，持续微小泄漏比一次峰值更有意义。

Record offered/received load, drop location, generator CPU/NIC, versions, topology and temperature. Classify failures as product defects, environment/generator limits or inconclusive tests rather than rerunning until green. In soaks, resource trends reveal slow leaks better than isolated peaks.
