Q1 · TRILL——你具体负责什么？Q1 · TRILL — what exactly did you own?

首席设计 + 核心实现：协议架构、状态机、拓扑计算(IS-IS 链路状态)、等价多路径转发、故障收敛、FIB/表项下发，以及与平台模块的接口。范围：协议 + 软件，不含交换机硬件或整机。Chief design + core implementation: protocol architecture, state machine, topology computation (IS-IS link-state), equal-cost multipath forwarding, failure convergence, FIB/table programming, interfaces to platform modules. Scope: protocol + software, not hardware or full-product.

Q2 · JEXEC——转发引擎还是芯片模拟器？Q2 · JEXEC — forwarding engine vs chip simulator?

JEXEC 在 x86/MIPS 软件数据面执行转发指令；同一模型也模拟转发芯片，让控制面/特性在流片前即可验证——本质是芯片的软件模型。JEXEC executed forwarding instructions in the software data plane on x86/MIPS. The same model also simulated the forwarding chip, validating control-plane/feature behavior before silicon — a software model of the ASIC.

Q3 · Broadcom bring-up + SDK——如何迁移到我们的栈？Q3 · Broadcom bring-up + SDK — and transition to our stack?

在 Broadcom 上 bring-up：芯片初始化、MIPS SDK 适配、平台集成、控制面基础设施、软件 FIB。分工：芯片/SDK 管表项/流水线；平台管初始化 + 控制面；PFE 做转发。迁移：芯片相关代码藏在 HAL/ops 表后，SDK 设计原则直接迁移——分层、版本化 ABI、规格生成、能力查询。Bring-up on Broadcom: chip init, MIPS SDK adaptation, platform integration, control-plane infra, software FIB. Division: chip/SDK = tables/pipeline; platform = init + control plane; PFE = forwarding. Transition: chip-specific code hides behind a HAL / ops table; SDK principles transfer — layering, versioned ABI, code-gen from specs, capability query.

Q4 · Daybreak / SRX1500——分离取舍与 DPDK 近线速？Q4 · Daybreak / SRX1500 — tradeoffs + DPDK near-line-rate?

把控制面(Linux/KVM VM)与数据面分离以获 HA 与独立重启；代价 = IPC + 复杂度。用 DPDK 轮询 + SR-IOV/VirtIO 绕过内核拷贝并锁定资源，达到近线速。取舍：独占 CPU、内存锁定、复杂度。Separated control plane (Linux/KVM VM) from data plane for HA / independent restarts; cost = IPC + complexity. Used DPDK poll-mode + SR-IOV/VirtIO to bypass copies and pin resources for near-line-rate. Tradeoffs: dedicated CPU, memory pinning, complexity.

Q5 · eBPF/XDP——哪一层，收益？Q5 · eBPF/XDP — which layer, what benefit?

把 XDP 挂到内核入口(驱动钩子)做早期过滤/分类；eBPF 做可编程策略。收益：更少拷贝、更低时延、线速抗 DDoS。取舍：校验器限制、程序复杂度、按 NIC 支持。Attached XDP to the kernel ingress (driver hook) for early filtering/classification; eBPF for programmable policy. Benefit: fewer copies, lower latency, line-rate DDoS mitigation. Tradeoffs: verifier limits, program complexity, per-NIC support.

Q10 · 如何设计一个全新 SDK？（约束/调研/方法/交付物）Q10 · How would you design a brand-new SDK? (constraints/research/method/deliverables)

① 先问约束（澄清优先）：目标芯片与 OS/架构；性能 SLA（吞吐/时延/规模）；兼容性与版本策略；安全边界；支持周期；团队与时间。约束没厘清，架构无从谈起。① Clarify constraints first: target chip and OS/arch; performance SLA (throughput/latency/scale); compatibility and versioning policy; security boundary; support lifetime; team and timeline. Architecture is meaningless before constraints are clear.

② 调研：用户与用例、现有 API/生态（SAI/NOS/开源）、竞品与标准、芯片能力(capability query)、可复用组件、失败与运维需求。② Research: users and use cases; existing APIs/ecosystem (SAI/NOS/open source); competitors and standards; chip capabilities (queryable); reusable components; failure and ops requirements.

③ 方法：分层与契约（门面/核心/资源/访问）；稳定 ABI（定宽类型、版本协商）；规格驱动 + 代码生成；变化点抽象为函数表/插件/策略回调；明确失败语义与生命周期（幂等、部分失败回滚、引用计数、ISSU/warm-boot）；性能（零拷贝、批处理、快慢路径分离）；可观测内建；原型先行（PoC 验证最大风险）。③ Method: layering and contracts (facade/core/resource/access); a stable ABI (fixed-width types, version negotiation); spec-driven code generation; abstract variation points as ops tables / plugins / strategy callbacks; explicit failure semantics and lifecycle (idempotency, partial-failure rollback, ref counting, ISSU/warm-boot); performance (zero-copy, batching, fast/slow path split); built-in observability; prototype first (PoC the biggest risk).

④ 交付物：架构文档与 ADR；接口规范/头文件(ABI)；参考实现与样例；测试与验证矩阵；兼容性矩阵与版本策略；性能基准与容量模型；迁移/升级与 ISSU 指南；调试工具与可观测面；发布/打包；开发者文档与可 demo 的 PoC。④ Deliverables: architecture doc + ADRs; interface spec/headers (ABI); reference implementation and examples; test/validation matrix; compatibility matrix and versioning policy; performance benchmarks and capacity model; migration/upgrade and ISSU guides; debug tooling and observability; packaging/release; developer docs and a demoable PoC.

Q11 · 你如何做架构决策？Q11 · How do you make architecture decisions?

框架：明确问题与约束 → 列备选 → 评估（记分卡：容量/时延/恢复上界/成本/风险）→ 决策并写 ADR → 用原型/基准验证 → 复盘。Framework: define problem and constraints → list options → evaluate (scorecard: capacity/latency/recovery bound/cost/risk) → decide and write an ADR → validate with prototype/benchmark → retrospect.

原则：用数据与实测，不用口号；区分“必需/期望”；优先可逆决策，不可逆决策多验证、后置提交；一次只改一个变量；明确状态所有者与失败语义。Principles: data and measurement over slogans; separate must-have/nice-to-have; favor reversible decisions, gate irreversible ones with more validation; change one variable at a time; make state ownership and failure semantics explicit.

常见权衡：内核/用户态、同步/异步、通用/专用、可移植性/芯片能力、吞吐/延迟、隔离/利用率。例：交换机数据面选内核驱动模型而非 DPDK 用户态驱动——因为转发在 ASIC、CPU 只处理慢路径，安全与单一所有者更重要。Common tradeoffs: kernel/user space, sync/async, general/purpose-built, portability/chip capability, throughput/latency, isolation/utilization. E.g. switch data plane chose a kernel-driver model over DPDK: forwarding is in the ASIC and the CPU only handles slow path, so safety and single ownership dominate.

记录与沟通：ADR 写背景/备选/选择/后果；让干系人参与；对齐验收标准；保留证据链。反模式：过早优化、隐式耦合、无 owner 的共享状态、静默降级、用 API 名代替理解。Record & communicate: an ADR captures context/options/choice/consequences; involve stakeholders; align on acceptance criteria; keep the evidence chain. Anti-patterns: premature optimization, hidden coupling, shared state without an owner, silent degradation, substituting API names for understanding.

↳ “每个决策我会写清：背景、备选、选择、后果、验证方式——这样别人能复审，未来能复盘。”"For each decision I record context, options, choice, consequences and how it's validated — so others can review it and we can revisit it."

Q12 · 系统设计：AI 集群无损以太网（RoCEv2 零丢包）Q12 · System design: lossless Ethernet for AI (RoCEv2 zero loss)

目标：零丢包、低尾延迟、可预测。手段：无损（PFC + ECN/DCQCN）或 ECN-only（视端点与验证）；按 BDP 与 T_stop 计算 buffer/headroom；拥塞参数端到端一致；哈希熵足够避免大流集中（ECMP/自适应路由）；优先级/QoS 映射一致；PFC 死锁预防（无环、优先级隔离）；遥测与排障。Goal: zero loss, low tail latency, predictability. Means: lossless (PFC + ECN/DCQCN) or ECN-only (per endpoints/validation); size buffer/headroom from BDP and T_stop; align congestion params end-to-end; enough hash entropy to avoid flow concentration (ECMP/adaptive routing); consistent priority/QoS mapping; PFC deadlock prevention (loop-free, priority isolation); telemetry and diagnosis.

交付：拓扑(Clos/Rail-optimized)、参数基线、验证矩阵(incast/微突发/多发送者)、故障恢复。观点：端点支持时优先 ECN-only，PFC 作兜底而非默认。Deliver: topology (Clos/rail-optimized), parameter baseline, validation matrix (incast/microburst/multi-sender), failure recovery. View: prefer ECN-only when endpoints support it; PFC as fallback, not default.

Q13 · 系统设计：支持 ISSU / warm-boot 的软件栈Q13 · System design: a stack that supports ISSU / warm-boot

分离“控制面状态”与“硬件转发状态”：冻结/排空变更 → 保存必要状态 → 保留硬件转发 → 恢复映射 → reconcile → 恢复协议/学习；设超时与 cold fallback。关键：状态所有者、generation、幂等、软硬对账、SAI warm-boot 语义；测试新流/旧流/路由变化/异常报文；名称不代表零丢包。Separate control-plane state from hardware forwarding state: freeze/drain → save → retain hardware forwarding → restore mappings → reconcile → resume protocols/learning; set timeouts and cold fallback. Key: state ownership, generations, idempotency, software/hardware reconciliation, SAI warm-boot semantics; test new/existing flows, route changes, exceptional packets; labels do not prove zero loss.

Q14 · 取舍：内核驱动 vs 用户态驱动（DPDK）Q14 · Tradeoff: kernel driver vs userspace driver (DPDK)

交换机：转发在 ASIC、CPU 只处理慢路径 → 内核驱动（安全、单一所有者、内核网络集成、中断/DMA 友好）。服务器/NIC：CPU 处理每包 → DPDK 用户态（零 syscall、轮询、最高吞吐），代价：独占 CPU、复杂度、隔离差、依赖 UIO/VFIO。按“谁处理数据面”决定。Switch: forwarding in the ASIC, CPU only slow path → kernel driver (safety, single ownership, kernel-network integration, IRQ/DMA friendly). Server/NIC: CPU processes every packet → DPDK userspace (no syscalls, polling, max throughput); cost: dedicated CPU, complexity, weaker isolation, needs UIO/VFIO. Decide by "who processes the data plane".

Q15 · SDK 演进：不破坏 ABI 加特性Q15 · SDK evolution: add features without breaking the ABI

稳定 ABI：定宽类型、显式对齐、保留字段、版本协商；新特性走新命令/新版本；能力查询让用户态适配；弃用走多版本窗口；规格驱动生成减少手改；维护兼容矩阵与 warm-boot 支持。Stable ABI: fixed-width types, explicit alignment, reserved fields, version negotiation; new features via new commands/versions; capability query so userspace adapts; deprecate over a multi-version window; spec-driven generation reduces hand edits; maintain a compatibility matrix and warm-boot support.

Q16 · 排障：PFC 风暴 / 尾延迟 / 丢包Q16 · Debugging: PFC storms / tail latency / loss

先由“何时开始、影响谁、最近变更”缩小范围，对比正常/异常路径同指标。PFC 风暴：沿暂停传播方向找最早持续暂停的队列/端点。尾延迟：微突发、hash 热点、ECN/CNP、NIC retry、GPU/PCIe。先保留现场再改配置。Narrow scope via onset, who is affected, recent changes; compare the same metrics on healthy vs failing paths. PFC storm: trace pause propagation to the earliest persistently paused queue/endpoint. Tail latency: microbursts, hash hotspots, ECN/CNP, NIC retries, GPU/PCIe. Preserve evidence before changing config.

Q17 · 判断力：资源有限时如何排优先级Q17 · Judgment: prioritizing under limited resources

用 影响面 × 风险 × 成本 排序；先做“解除阻塞”和“高风险去风险”的 PoC；区分必需/期望；可逆决策先做、不可逆后置并多验证；与产品/市场对齐验收标准。Rank by impact × risk × cost; first do "unblockers" and high-risk de-risking PoCs; separate must-have/nice-to-have; take reversible decisions first, gate irreversible ones with more validation; align acceptance criteria with product/marketing.

Q18 · 影响力：如何说服反对的团队/资深工程师Q18 · Influence: convincing a dissenting team or senior engineer

先理解对方约束与数据；用可复现的基准/原型而非立场；小步 PoC 降风险；把决策写成 ADR 便于复审；找共同验收标准；用数据/实验而非权威。Understand their constraints and data first; use reproducible benchmarks/prototypes, not positions; small PoCs to de-risk; write an ADR for review; find shared acceptance criteria; persuade with data/experiments, not authority.

Q19 · 复盘：讲一个失败/被推翻的设计Q19 · Retrospective: a failed or overturned design

用 STAR：背景 → 我的判断 → 结果 → 复盘 → 改变。强调学到的方法论（如过早优化、忽视反馈延迟、状态所有者不清）。诚实 + 成长比“没有失败”更有说服力。Use STAR: context → my call → outcome → retro → change. Emphasize the methodology learned (premature optimization, ignoring feedback delay, unclear state ownership). Honesty + growth beats "no failures".

Q20 · 学习力/观点：陌生领域上手 + 以太网 vs IB / UECQ20 · Ramp-up / opinion: new domain + Ethernet vs IB / UEC
