Warm / Cold 区别

Warm / cold distinction

Cold 通常重置并重建较多设备状态；warm 是否保留 route、FDB、queue 和 link 取决于硬件/SDK。

Cold typically resets/rebuilds more state; warm retention of routes/FDB/queues/links depends on hardware/SDK.

进程 restart、内核 reboot、firmware reset、ASIC reset 是不同事件，不能用统一名称推断保留集合。

Process restart, kernel reboot, firmware reset and ASIC reset are distinct events with different retention sets.

BGP GR 与 BFD

BGP GR & BFD

BGP GR 通过能力与重启相关状态允许邻居暂时保留 stale 路由；End-of-RIB 标识相应更新阶段完成。

BGP GR capabilities/state allow temporary stale-route retention; End-of-RIB marks completion of an update phase.

BFD 活性检测可能更早宣告路径失败；GR、BFD 和实际转发保留必须匹配，否则会保留黑洞或过早撤路。

BFD may detect failure earlier. GR, BFD and actual forwarding retention must align to avoid stale black holes or premature withdrawal.

SDK 对象重建

SDK object reconstruction

已保留硬件对象与新进程中的 OID/引用需要重新对应。

Retained hardware objects must be remapped to new process handles/references.

某些 SDK 提供 warm state 存储和初始化模式，但文件存在并不保证与当前固件兼容；恢复应区分硬件表、软件句柄和协议邻接三层。

SDK warm-state storage/init modes may exist, but stored data must match firmware. Distinguish hardware tables, software handles and protocol adjacencies.

Counter / Learning

Counters & learning

重启可改变 counter 起点与 MAC aging 所有者。

Restarts can alter counter baselines and MAC-aging ownership.

若硬件继续学习而软件停机，恢复后仅重放旧 FDB 会遗漏移动；需要设备支持的学习通知或表读取。保留转发不代表学习与统计也完全连续。

If hardware learns while software is down, old FDB replay misses moves; notifications/readback must capture them. Retained forwarding does not guarantee uninterrupted learning/statistics.

状态保留清单

State-retention inventory

对 MAC、route、neighbor、ACL、QoS、端口、计数器和协议会话逐项记录：存在哪里、谁重建、允许陈旧多久、恢复前能否接流量。数据面保留与控制面 GR 是不同机制；邻居或链路变化可能让保留转发迅速失效，需明确动态事件处理。

For MACs, routes, neighbors, ACLs, QoS, ports, counters and sessions, record location, reconstruction owner, allowed staleness and readiness gating. Data-plane retention differs from protocol GR; neighbor/link changes can invalidate retained forwarding, requiring explicit event handling.
